# 時刻計算・制約チェック

旅程(trip_places)のstart_time / end_timeを埋める仕組み。

## update_schedule

Phase 1では以下の割り切りとする。

- 訪問順(visit_order)は変えない
- 旅行の開始時刻から、移動時間と滞在時間を前から順に足してstart_time / end_timeを埋める
- 制約違反(営業時間外、終了時刻超過)は警告表示のみ。自動修正・並び替え最適化はしない

順序最適化(移動を少なくする等)はPhase 2以降で検討する。

旅程の追加・削除・並び替え・滞在時間の変更、旅行の日時の変更のたびに自動で計算し直す。

## 移動時間

前の地点からの移動時間をtrip_placesの`travel_minutes`に保存する(1件目はNULL)。start_time / end_timeと同じく計算して保存する値。

### 直線距離による計算

徒歩を想定する。経路検索APIが使えないときの代わりとしても使う。

移動時間(分) = 直線距離(km) × 迂回係数 ÷ 速度(km/h) × 60 (切り上げ)

- 直線距離: 緯度経度から球面上の距離を求める(haversine式)
- 速度: 4.8km/h(徒歩1分=80m)
- 迂回係数: 1.3(道は直線ではないため)
- 切り上げ: 短く見積もると予定が崩れるため、安全側に倒す

### 経路検索API

openrouteservice(OpenStreetMapのデータを使う経路検索サービス)で、道に沿った徒歩の所要時間を取る。

**未実装(2026-10-28時点)**: openrouteservice.org のサイトが停止中でAPIキーを登録できないため保留。現在は直線距離による計算のみで動いている。復旧したらキーを取得して実装する。

- Matrix APIを使い、時刻計算1回につきAPI呼び出しを1回にまとめる(旅程の件数に関係なく1往復)
- 失敗したとき(回数制限・サーバー停止・ネット不通)は直線距離による計算で代用する
- 結果を保存するテーブルは作らない。一人で使う範囲では無料枠に届かないため。利用者が増えて回数制限が問題になったら(Phase 3)検討する
- APIキーは`.env`に置く
- LLMに移動時間を推測させない(開発原則: 時間・距離をAIに推測させない)

電車・バスなど移動手段の区別は後回し(検討事項「時刻の固定」を参照)。

## 制約チェック

- 旅行の終了時刻: 旅程の最後のend_timeが旅行のend_atを超えたら警告する(手順6)
- 営業時間: Phase 2で外部の場所検索から営業時間を取るようになってから作る。opening_hoursの形式もそのとき決める

## 検討事項(後回し)

- **時刻の固定(予約・交通機関の出発)**: 予約のように「場所に着く時刻」を固定する場合はtrip_placesに`fixed_start_time`(NULL可)、バスのように「移動の出発時刻」を固定する場合は、その区間に`travel_mode`(徒歩/バス/電車など)と`depart_at`(NULL可)を持たせる案。備考などの自由文には書かない(プログラムが読めず計算できないため)。プログラムは守れるか計算・判定し(早く着けば待ち時間、遅れれば警告)、AIは間に合わないときの組み替えを提案し、人間が確定する。時刻表はPhase 1では手入力、将来は公共交通の経路検索APIから取る
- **場所未定の仮置き**: 「そのへんのカフェで30分」のように場所を決めずに予定を入れる。trip_placesの`place_id`をNULL可にし、`label`(例: カフェで休憩)を追加する案。座標が無いので、仮置きは直前の場所の近くとみなし、直前からの移動は0分、次への移動は直前の場所の座標から計算する。場所が決まったらplace_idを入れて確定する。placesにダミーの場所を登録する方法は、共有の辞書が汚れ並び替えで座標が合わなくなるため採らない
