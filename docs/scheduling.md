# 時刻計算・制約チェック

旅程(trip_places)のstart_time / end_timeを埋める仕組み。

## update_schedule

Phase 1では以下の割り切りとする。

- 訪問順(visit_order)は変えない
- 旅行の開始時刻から、移動時間と滞在時間を前から順に足してstart_time / end_timeを埋める
- 制約違反(営業時間外、終了時刻超過)は警告表示のみ。自動修正・並び替え最適化はしない

順序最適化(移動を少なくする等)はPhase 2以降で検討する。

## 移動時間

Phase 1では徒歩を想定した仮実装とする。

移動時間(分) = 直線距離(km) × 迂回係数 ÷ 速度(km/h) × 60 (切り上げ)

- 直線距離: 緯度経度から球面上の距離を求める(haversine式)
- 速度: 4.8km/h(徒歩1分=80m)
- 迂回係数: 1.3(道は直線ではないため)
- 切り上げ: 短く見積もると予定が崩れるため、安全側に倒す

電車・バスなど移動手段の区別は後回し(検討事項「時刻の固定」「移動手段」を参照)。

## 制約チェック

営業時間・旅行の終了時刻のチェック。opening_hoursの形式とあわせて手順6で決める。

## 検討事項(手順5で決める)

- **時刻の固定(予約・交通機関の出発)**: 予約のように「場所に着く時刻」を固定する場合はtrip_placesに`fixed_start_time`(NULL可)、バスのように「移動の出発時刻」を固定する場合は、その区間に`travel_mode`(徒歩/バス/電車など)と`depart_at`(NULL可)を持たせる案。備考などの自由文には書かない(プログラムが読めず計算できないため)。プログラムは守れるか計算・判定し(早く着けば待ち時間、遅れれば警告)、AIは間に合わないときの組み替えを提案し、人間が確定する。時刻表はPhase 1では手入力、将来は公共交通の経路検索APIから取る
- **移動時間の保存**: trip_placesに`travel_minutes`(前の地点からの移動時間、1件目はNULL)を追加する案。start_time / end_timeと同じく計算して保存する値。タイムライン表示に必要で、外部の経路APIを使うと毎回の再計算が高コストになり、人が上書きしたくなる可能性もあるため
- **場所未定の仮置き**: 「そのへんのカフェで30分」のように場所を決めずに予定を入れる。trip_placesの`place_id`をNULL可にし、`label`(例: カフェで休憩)を追加する案。座標が無いので、仮置きは直前の場所の近くとみなし、直前からの移動は0分、次への移動は直前の場所の座標から計算する。場所が決まったらplace_idを入れて確定する。placesにダミーの場所を登録する方法は、共有の辞書が汚れ並び替えで座標が合わなくなるため採らない
